# 项目过程与上下文维护

维护当前有效的项目状态，并为详细依据提供入口，使后续对话或 agent 能接续工作。配合“理解需求 → 检查实现 → 提出方案 → 明确确认 → 开发 → 验证 → Code Review → 交付”，不替代项目开发规范，也不因维护记录而扩大业务实施权限。

## 判断是否需要记录

- 范围明确、预计一轮即可完成并验证的小需求，正常执行，不默认建立项目资料。
- 已有项目的小调整，按需读取相关记录；只有改变长期有效的规则、方案、进度、阻塞或验证结论时才更新。
- 多阶段、跨会话、重要业务规则或技术取舍、跨仓库协调，或用户明确要求记录时，适合建档。以实际上下文和交接需要判断，不按文件数、代码行数或固定条件数量判断。
- 任务中途扩大时，可以启用记录，整理当前会话及可访问资料中有依据、仍有效的信息，无需补写完整会话历史。

用自然语言识别三类意图，无需专用命令：

- **建立项目记录**：确定归属，整理已确认背景和当前状态，仅创建本次需要的资料。
- **接手已有工作**：定位现有主文件，读取当前任务相关依据，核实本次涉及的工作区后继续已授权工作；接手本身不表示允许写入。
- **同步项目记录**：根据有实质影响的新结论，按当前文件分工更新具体资料，再同步全局视图；并行协作按下文报告与汇总规则执行。

用户明确要求建立、同步或维护记录，或已有明确的项目维护授权时，在该范围内随重要变化持续维护，不逐条重复确认。没有维护授权时先只读，确需写入再确认维护范围。本轮明确只读、只分析或不落盘时保持只读；已有记录、未来计划和 Skill 调用本身不构成业务实施授权。

## 定位资料，按需读取

默认根目录为 `~/Documents/progress/`，用户指定其他位置时遵从用户。每个项目或独立需求使用自己的稳定目录：

```text
<资料根目录>/<项目或独立需求名称>/
  process.md
  requirements/    # 需要保存需求细节时创建
  designs/         # 需要保存方案或实现依据时创建
  tests/           # 需要保存测试资料时创建
  agent/           # 确有并行协作需要或用户明确要求时启用
    <需求>-<分工或会话标识>-<阶段>.md
    archive/       # 完成汇总后按需创建，保留原始报告
```

用户或项目接入说明已给出目录时，直接定位并读取其背景。未给出时，先查看根目录的直接子目录名称，再核对有根据的候选 `process.md`；不要遍历全部项目、历史资料或其他对话。创建前检查目录是否已有内容，避免重复建档或误写到其他项目；只有无法可靠判断归属时才询问。

持续推进的大项目按项目划分，子需求归入该项目；可以独立实施、验收和交接的需求也可独立划分。同一项目的不同对话、多个仓库和 worktree 共用一套资料，不按对话或工作区另建项目目录。目录名称保持稳定，当前阶段写在主文件中。

先读 `process.md`，通过其中链接定位当前任务。再按分析、设计、实现、测试、Review 或交接需要读取相关部分，不默认加载全部附件。链接缺失或失效时，只查找与当前任务有关的可访问依据，不能补造历史事实。

需要新建或调整文档结构时，按需读取 [references/templates.md](references/templates.md) 的对应模板；需要业务项目接入片段时读取其中“AGENTS.md 接入片段”。模板是裁剪起点，不是必须整套创建的清单。

## 各文件保存什么

- **`process.md`**：简短目标、背景和范围；仓库、系统与工作区；各需求当前推进程度、实现摘要、验证情况和资料链接；阻塞、待确认问题、下一步及必要的近期关键变化。保持导航和总进度职责，不无限追加会话日志。
- **`requirements/`**：按需求保存目标、已确认业务规则、范围、验收条件、待确认问题及重要调整。
- **`designs/`**：按需求保存技术方案、调用流程、必要契约、修改范围、兼容影响与取舍；实现摘要和必要 Review 记录先放在相应方案中。
- **`tests/`**：按需求保存用例、预期结果、实际执行结果，以及需要保留的样例或独立验证脚本。通常先一项需求一个 Markdown，有实际样例或脚本时再建子目录。正式测试源码继续随业务代码维护，这里链接其位置和执行方法。
- **`agent/`**：直接存放当前项目协作 agent 已提交、尚未汇总的阶段报告；`agent/archive/` 保留已经完成汇总的原始报告。仅在需要时启用，不预建空目录。

背景和工作区先放在 `process.md`，实施记录先放在对应需求或方案中；增长到影响阅读时，才按需拆出 `background/`、`records/` 等目录。已有文档通过链接纳入，不复制出第二份维护。沿用已有需求编号或稳定名称关联需求、方案、实现位置和测试，不另建编号体系，不预建空目录或占位文档。

工作区信息记录本机路径、职责、使用的分支和 worktree、必要提交或改动状态，以及最近核对时间。这些是带时间的观察结果；接手开发时重新核实本次涉及的工作区，不把旧记录当作实时状态，也不要求每次检查全部仓库。

## 何时及如何更新

需求、规则或范围确认及调整，方案确定或改变，完成可交接的实现阶段，获得重要测试或 Review 结果，出现影响后续工作的阻塞，以及交接或结束一轮有实质进展的工作时保留有效结论。并行协作先按分工提交报告，正式资料由主 agent 按下节规则汇总。普通问答、重复解释和未形成结论的探索不逐轮落盘；没有实质变化时保持文件原样。

单 agent 工作按以下顺序直接维护正式资料；并行时由主 agent 执行这些更新，协作 agent 只提交各自独立的阶段报告：

1. 重新读取当前文件和本次结论的依据，局部更新发生变化的具体资料，保留用户和其他对话的无关内容。并发改动导致同一内容含义不明时，先澄清冲突再修改。
2. 检查该变化是否影响相关需求、方案、实现说明、验收条件或测试资料，只同步实际受影响的部分。
3. 同步 `process.md` 的当前状态、资料链接、阻塞和下一步。实现情况和验证情况分开表达，例如“后端已实现；前端待适配；离线测试通过；真实接口待联调”。

重要变化保留简短日期、变化内容和原因；旧方案被替代时，在相关位置标明替代关系并指向当前有效结论，避免新旧规则并列生效。只保留会影响后续工作的过程信息，详细依据留在对应资料中。

项目结束后保留原目录，由负责正式资料维护的 agent 在主文件写清最终交付、实际验证情况和遗留事项。交付时简要说明本轮更新或提交了哪些资料、能确认什么及下一步，不把记录维护当作业务实施或验收完成。

## 并行协作：阶段报告、汇总与归档

### 启用与文件分工

仅在确有并行协作需要或用户明确要求时启用 `agent/`。先明确负责汇总的主 agent，以及各协作 agent 的任务和报告文件范围；可在 `process.md` 简记，不另建人员或任务管理系统。

默认由主 agent 维护 `process.md` 及实际受影响的需求、方案和测试资料。协作 agent 完成自己的业务任务，将有交接价值的成果提交到各自独立的报告，不同时争写公共文件。协作方不能因为达到阈值而自行认领主 agent 身份，可以在交付中提示待汇总情况并按已确认的协作方式交接。单 agent 继续沿用原流程；Git 版本管理不能替代公共目录的文件分工，本流程不自行初始化 Git 仓库。

### 提交阶段报告

使用 `<需求>-<分工或会话标识>-<阶段>.md` 区分报告，复用已有标识，不新建复杂编号协议。仅提交已经形成阶段结论的报告，不记录每轮聊天或完整工具日志；提交后保持原文稳定，新阶段进展另写文件。

按需说明实际成果、工作区与代码基线、验证及未验证项、重要发现、已确认变化与待确认建议、阻塞、下一步和建议更新的资料，并提供可定位依据。使用 [阶段报告模板](references/templates.md#阶段报告)，可省略无意义字段。报告中的建议、计划、实现和验证分别表达，不能直接当作验收通过。

### 主 agent 检查阈值

主 agent 在接手工作或阶段交付时，检查当前项目 `agent/` 直接存放的已提交、尚未汇总报告；根据归属和提交情况识别，不只按扩展名计数。`archive/` 中的报告、草稿和无关文件不计入。

- 达到或超过 **3 份**，执行一次汇总。
- 不足 3 份，普通阶段报告可继续积累。
- 涉及已确认需求或方案变化、影响其他 agent 的阻塞、重要阶段结束、交接或项目结束时，可以提前汇总。

阈值只是当前主 agent 执行时的检查条件，不增加后台监听、定时任务或跨对话自动唤醒。达到阈值也不改变当前只读要求或授权范围；只读时说明待汇总情况，不写入或归档。

### 汇总与归档

1. 明确本次待处理报告的具体文件清单；只处理选定报告，期间新提交的文件留待下一轮。
2. 阅读报告，按需核对关键代码、工作区和验证依据。
3. 对冲突、缺失依据或超出授权范围的内容保留待确认状态，不按时间新旧直接采纳，不把建议变成已确认规则。
4. 局部更新实际受影响的需求、方案和测试资料，再同步 `process.md` 的当前进度、验证情况、阻塞和下一步。
5. 核对重要结论、未解决事项和必要依据已如实保留，并明确报告与正式资料的对应关系。汇总不代表验收通过，已纳入的待确认事项仍保持待确认。
6. 仅将本次选定且全部内容已完成整合并核对的报告逐份移入 `agent/archive/`，保留原文，并同步正式资料中的必要引用到实际归档路径。目标同名文件已存在时不覆盖，先核对归属。

无法整合或仍有未处理内容的报告继续留在 `agent/`，说明具体原因；不能因为读过报告就归档。正式资料更新失败或尚未完成核对时，不提前归档。不通过批量移动整个目录，将新到报告或未处理报告一起归档。

汇总后先归档，不删除。可以精简正式资料的重复表述、合并相同结论，并标明过时结论的替代关系；保留重要调整原因、未解决事项和复盘依据。归档报告保留原始内容，不再计入待汇总阈值。不设置自动删除、保留期限或归档清理任务，不连带删除测试样例、验证脚本或其他依据文件。

## 依据与验证口径

用清楚的文字区分用户已确认规则、尚未确认建议、未来计划、代码实际实现、实际执行的验证和待核实信息，不设计复杂状态枚举。只整理当前会话及可访问资料中有依据的信息，缺失项明确标注。

重要结论提供可定位依据，如用户确认的日期和内容、文档链接、代码路径与类或方法符号、测试结果位置；行号仅作辅助。记录与当前用户要求、代码或实际结果冲突时，说明差异和依据，不能默默混成一个结论；已确认的新规则也不能被记成代码已经实现。

实际验证保留必要的时间、代码基线（提交及相关未提交改动）、环境、执行方式、结果和覆盖范围。区分编译通过、测试代码编译通过、实际执行测试、Mock、真实数据库/RPC/消息/浏览器或端到端联调；静态审阅与情景推演单独说明。未执行项明确写明，测试用例的预期结果不能填入实际通过结果。

不写入凭据、token 等敏感值；保留必要的脱敏结果和可定位依据即可。
