# 项目记录模板

按需使用：[主文件](#processmd)、[需求](#需求资料)、[方案](#方案资料)、[测试](#测试资料)、[阶段报告](#阶段报告)、[项目接入片段](#agentsmd-接入片段)。

以下内容供裁剪，不是必填表单。只创建当前需要的文件，花括号表示待填写内容；不适用的部分可省略，影响后续工作的缺失信息明确写“待核实”或“待确认”。沿用已有需求编号或稳定名称，不新建编号体系。相对链接以实际文档位置为准，链接已有资料时不再复制正文。

## process.md

放在项目资料目录根部。保留当前全局视图，细节放入链接指向的资料。

```markdown
# {项目或独立需求名称}

最近实质更新：{日期和时区}

## 目标、背景与范围

{简短说明目标、必要背景、已确认范围和当前阶段。已有背景资料可链接。}

## 仓库、系统与工作区

| 仓库或系统及职责 | 本机仓库 / worktree 路径 | 使用分支 | 代码基线及必要改动状态 | 最近核对时间 |
| --- | --- | --- | --- | --- |
| {名称与职责} | {绝对路径，必要时区分主仓库和当前 worktree} | {实际观察值} | {提交及相关未提交改动，或非 Git / 待核实} | {日期、时间、时区} |

{同一项目可有多个仓库或 worktree。此表为观察结果，接手时核实本次相关项。}

## 并行协作分工

{仅在启用并行协作时保留本节；由主 agent 维护，不预建空的 agent/ 或 archive/。}

- 主 agent：{已明确的报告汇总及正式资料维护负责人或会话标识。}
- 协作 agent：{标识、负责的任务及独立报告文件范围；按实际参与者填写。}

## 需求推进与资料入口

| 需求 | 当前推进程度与实现摘要 | 实际验证与待验证项 | 依据与资料 |
| --- | --- | --- | --- |
| {已有编号或稳定名称} | {已确认 / 方案待确认 / 已实现部分，按事实描述} | {已执行的验证类型与结果；未执行部分} | [需求](requirements/{稳定名称}.md) · [方案](designs/{稳定名称}.md) · [测试](tests/{稳定名称}.md) |

{只保留真实存在的链接；已有外部文档和正式测试源码可以直接链接。}

## 阻塞、待确认与下一步

- {影响后续工作的阻塞或待确认问题，附依据和解除条件；存在无法整合的报告时，链接待汇总文件并说明具体原因。}
- {下一步具体工作，以及尚需取得的业务实施授权（如有）。}

## 近期关键变化

- {日期}：{变化及原因；需要时链接详细结论及本次已汇总报告的实际归档路径。只留影响后续工作的近期摘要，不另建报告索引。}

## 最终交付与遗留事项

{仅在项目结束时填写：交付范围、实际验证、未验证或未解决事项及后续入口。保留原目录。}
```

## 需求资料

按需保存为 `requirements/{已有编号或稳定名称}.md`；已存在需求文档时直接链接并维护其原位置。

```markdown
# {需求名称}

关联：[项目主文件](../process.md) · [当前方案](../designs/{稳定名称}.md)

## 目标与范围

{要解决的问题、预期行为、已确认实施范围与必要边界。}

## 当前业务规则与验收条件

- {规则或验收条件；注明用户已确认、仍待确认或只是建议，并给出依据。}

## 待确认问题

- {问题、影响及确认后需要同步的位置；没有则省略。}

## 重要调整

- {日期}：{调整内容、原因与确认依据；若替代旧规则，指向当前规则。}
```

## 方案资料

按需保存为 `designs/{已有编号或稳定名称}.md`。方案、实现和 Review 放在同一文档中时，区分计划与实际结果。

```markdown
# {需求名称}：当前方案与实现依据

关联：[需求](../requirements/{稳定名称}.md) · [测试](../tests/{稳定名称}.md)

## 当前方案与确认依据

{方案内容、确认情况与依据；尚未确认的建议明确标注。}

## 调用流程、契约与修改范围

{相关仓库、模块、代码路径和关键符号；必要调用流程、接口或数据契约。只展开实际涉及的内容。}

## 兼容影响与取舍

{选择原因、实际兼容影响与已知限制；没有必要时省略。}

## 实现情况

{已实现部分、尚未实现部分及可定位的代码依据；不要将方案写成实现事实。}

## Review 记录

{日期、审阅范围及代码基线、实际发现和结论、尚待验证事项。未做 Review 时明确写未执行，不预填通过。}

## 重要变化

- {日期}：{变化、原因和依据；被替代方案的简短说明及当前结论入口。}
```

## 测试资料

先保存为 `tests/{已有编号或稳定名称}.md`。有实际样例或独立验证脚本时，再按需创建同名子目录，并在文档中链接文件与运行方法。正式测试源码继续放在业务仓库，不复制到此目录。

```markdown
# {需求名称}：验证资料

关联：[需求](../requirements/{稳定名称}.md) · [方案](../designs/{稳定名称}.md)

## 用例与预期

| 场景与目的 | 输入 / 前置条件 | 执行方式 | 预期结果 |
| --- | --- | --- | --- |
| {业务规则或已知问题} | {必要的脱敏数据与条件} | {操作、命令或正式测试源码及符号} | {应发生什么，不代表已执行} |

## 实际执行记录

### {执行时间及其时区}：{本次验证名称}

- 代码基线：{仓库 / worktree、提交及本次相关未提交改动。非代码检查写实际资料版本；缺失则待核实。}
- 环境：{实际执行环境与必要依赖，不记录敏感值。}
- 验证类型与范围：{静态审阅 / 情景推演 / 编译 / 测试代码编译 / 实际测试执行 / Mock / 具体真实联调层次，按事实描述。}
- 执行方式：{实际命令、操作，或对应测试位置和运行方法。}
- 实际结果与依据：{实际观察结果、必要脱敏输出或结果文件链接；未执行就明确写未执行。}
- 限制与未验证项：{哪些链路没有覆盖，不能据此确认什么。}

{只有实际执行后才新增执行记录；不同基线或环境的结果分开记录。}

## 样例、脚本与正式测试入口

- {有实际文件或既有测试时，链接位置并说明用途和执行方法；没有则省略。}

## 待执行与阻塞

- {待执行范围、阻塞依据和下一步。预期结果不得记为实际通过。}
```

## 阶段报告

仅在确有并行协作需要或用户明确要求时使用，保存为 `agent/{需求}-{分工或会话标识}-{阶段}.md`；复用已有标识，只提交形成阶段结论的报告。已有草稿应明确标注，不计入待汇总报告。提交后保持稳定，新阶段另写文件；报告人不直接改写公共正式资料。

为保证移动到 `agent/archive/` 后仍可定位，报告中的代码、文档和结果依据使用绝对路径、完整 URL，或明确注明基准目录的路径，避免依赖报告当前目录的相对链接。主 agent 归档时保留原文，正式资料中的报告引用随归档位置同步。

```markdown
# {需求名称}：{分工或会话标识} · {阶段}

- 任务归属：{所属项目、已有需求编号或稳定名称，以及本次分工。}
- 报告人或会话标识：{已使用的标识。}
- 时间与阶段：{日期、必要时间与时区、当前阶段。}
- 提交说明：{本次已形成的阶段结论与交接范围；如仍是草稿则明确标注，不计入待汇总。}

## 实际完成与实现依据

{本次实际完成内容；相关仓库、worktree、分支、必要提交及相关未提交改动、文件路径与关键符号。计划内容另行标注，不当作已实现。}

## 实际验证与未验证项

{按实际需要写验证时间、基线、环境、执行方式、类型、结果与范围，并链接依据。编译、测试代码编译、测试执行、Mock 和真实联调分别说明；未执行项明确写未执行。}

## 重要发现与变化

{重要发现、已确认变化及其依据；待确认建议、冲突或缺失依据分别写明，不作为已确认规则或已验证事实。}

## 阻塞、下一步与交接

- {实际阻塞、影响及下一步；没有则省略。}
- 建议主 agent 更新：{具体需求、方案、测试资料或 process.md 的位置、建议内容和依据。}

{报告可裁剪；只保留有交接价值的内容，不附完整聊天或工具日志。}
```

## AGENTS.md 接入片段

供以后由用户接入业务项目；本 Skill 的创建或调用不自动修改任何 AGENTS.md。复制前将目录占位符替换为该项目稳定的实际资料目录，默认根目录是 `~/Documents/progress/`。多仓库和多个 worktree 指向同一个项目资料目录；目录可以尚未创建，不要求为了接入而建立空档案。

```markdown
## 项目过程与上下文

本项目资料目录：`{项目资料目录的绝对路径}`。

多阶段、跨会话、涉及重要规则或技术取舍、跨仓库协调，或用户明确要求记录时，使用 `$project-progress`。先读该目录的 `process.md`，再按当前任务读取相关需求、方案和测试资料；小需求不默认建档，不遍历全部历史。

在用户已授权的记录维护范围内，单 agent 随重要变化先更新具体资料，再同步 `process.md`；无实质变化不写入。本轮只读、只分析或不落盘时保持只读。多仓库和 worktree 共用此目录，接手时核实本次相关工作区。

确有并行协作需要或用户明确要求时，明确主 agent、各协作 agent 的任务和报告文件范围。协作方将阶段成果提交到 `agent/` 的独立报告，不争写公共文件，也不自行认领主 agent；正式资料默认由主 agent 维护。

主 agent 在接手或阶段交付时检查：当前项目已提交、尚未汇总的报告达到 3 份则汇总；不足时可积累，重要变化、影响其他 agent 的阻塞或重要阶段结束、交接、项目结束时可提前汇总。归档、草稿和无关文件不计数。只处理选定报告，正式资料更新并核对后才将已整合原报告移入 `agent/archive/`，保留原文和引用，不删除；新到或未处理报告留待后续。不预建空目录或增加后台任务。

区分确认规则、建议、计划、实际实现和实际验证，保留可定位依据。维护记录不扩大业务实施权限。
```
